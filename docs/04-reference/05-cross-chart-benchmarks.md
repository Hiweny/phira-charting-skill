# 横向基准：8 张谱的量化体检

> 结论先行：**精品谱之间的差异不在"音符多少"，而在"每颗音符背后花了多少帧"。**
> 本页数据由 [`tools/chart_stats.py`](../../tools/chart_stats.py) 全自动生成，可复现。

## 0. 怎么复现

```bash
python3 tools/chart_stats.py samples/*              # Markdown 表格
python3 tools/chart_stats.py samples/enchanted --json   # 单谱全字段
python3 tools/chart_stats.py samples/enchanted --timeline   # 每 10 秒事件密度
```

它回答的不是"好不好听"，而是**作者把时间花在哪了**：

| 指标 | 它真正衡量什么 |
|---|---|
| `判定线` | 舞台规模（多少块独立运动的面板） |
| `非默认贴图线` | 美术投入（有多少线用的是自制图） |
| `贴图` | 素材库大小 |
| `事件帧` / `帧每秒` | 编排密度（手 K 的工作量） |
| `帧/音符` | **这是动画还是谱面**的分界线 |
| `峰NPS` / `均NPS` | 演奏强度与爆发 |
| `Hold%` | 长条作为"呼吸"的使用比例 |

## 2. 五个能直接用的结论

### 2.1 密度主力是 **Drag**，不是 Flick（实测 0%~83%）

> ⚠️ 本条 v2 修正：v1 把 RPE 的 `type` 映射写错了
> （正确是 `1=Tap, 2=Hold, 3=Flick, 4=Drag`，以 prpr 源码为准），
> 导致 Drag 与 Flick 的统计互换。下面是修正后的真实构成。

| 谱面 | Tap | **Drag** | Hold | Flick |
|---|---|---|---|---|
| 83844（社区随机） | 7% | **83%** | 7% | 3% |
| 浮生梦 探窗 | 31% | **54%** | 10% | 4% |
| Night Drawmers | 39% | **48%** | 10% | 2% |
| 声嘶力竭 | 44% | **47%** | 5% | 4% |
| 鳥の詩 | 42% | **32%** | 18% | 8% |
| enchanted love | 44% | **31%** | 18% | 7% |
| 巴拉莱卡 | 56% | 23% | 16% | 4% |
| 84336（Lv.18） | **84%** | 10% | 5% | 1% |
| 稻香 | 59% | 10% | **27%** | 4% |

**Flick 在所有样本里都只有 1%~15%**，它不是密度来源。
真正的"便宜密度"是 **Drag**：不需要抬手、不需要精确 x、判定宽松，
天然适合铺满高 BPM 的十六分音符。

可操作规则：

```
技术向（需要定位压力）：Tap 60%~85%，Drag ≤ 20%，Flick ≤ 5%
爆发向（要爽感）    ：Tap 35%~45%，Drag 45%~55%，Flick 5%~10%
叙事/慢歌           ：Tap 55%~60%，Hold 25%~30%，Drag ≤ 15%
```

**Hold 是"呼吸"，不是密度**：稻香（慢歌）Hold 27%，高难谱普遍 5%~10%。
Hold 一多，读谱会变成"等长条"，节奏感立刻塌。

| 类型 | 心理作用 | 用法 |
|---|---|---|
| Tap | 击打点 | 主骨架，占 40%~85% |
| Drag | 流动 | 铺密度、连段、装饰 |
| Hold | 呼吸 | 长音、换气、段落收尾 |
| Flick | 强调 | 只在重音处，1~2 个就够 |

`DNA` 是另一类：Hold 9%、峰 NPS 29、帧/音符 3.3 —— 纯演奏向也成立，
它靠的是**高密度副歌**而不是演出。

### 2.2 演出型谱面的 X:Y 位移比透露"画布还是舞台"

| 谱面 | moveX | moveY | X:Y | 说明 |
|---|---|---|---|---|
| Night Drawmers | 11 998 | 4 049 | **3.0 : 1** | 横向运镜为主，像镜头推拉 |
| enchanted love | 4 751 | 3 890 | 1.2 : 1 | 舞台有纵深，双向都动 |
| 浮生梦 探窗 | 8 223 | 7 599 | **1.1 : 1** | 接近 1:1 → 全屏作画 |
| 声嘶力竭 | 2 776 | 2 324 | 1.2 : 1 | 均衡 |
| 鳥の詩 | 3 602 | 2 297 | 1.6 : 1 | 偏横向 |

**X:Y ≈ 1 时，作者是在"用判定线画画"**（探窗把线当笔，一帧一帧拼图案）。
**X:Y > 2.5 时，作者是在"做镜头"**（Night Drawmers 的线像摄像机轨道）。

想画图案就别怕 Y 多；想稳手感就让 Y 少动，M 型走位会毁掉读谱。

### 2.3 变速是"演出"，不是"难度"

| 谱面 | speedEvents |
|---|---|
| enchanted love | **602** |
| 鳥の詩 | 286 |
| 声嘶力竭 | 227 |
| Night Drawmers | 221 |
| 浮生梦 探窗 | **37** |

探窗几乎不变速（37 次），却拿到 46.3 帧/音符 —— 但见 §2.6，那个数字大半是烘焙出来的。
反过来说：**变速一多，读谱成本立刻上升**，没有画面支撑的变速是在给玩家添堵。

### 2.4 3D（incline）在样本里是 0

8 张谱，`inclineEvents` 有效值全为 0。也就是说：

- 3D 判定线在社区精品谱里**尚未成为标配**
- 它是**差异化机会**：用得好是记忆点，用不好是眩晕源
- 建议：一条谱最多 2~3 段 incline，且只用于"镜头俯冲/翻转"的瞬间

### 2.5 时长与线数是弱相关，与帧数才是强相关

稻香 223 秒只有 8 632 帧；探窗 129 秒却有 18 245 帧。
**线数不重要，帧/秒才重要。** 一条线可以撑 30 秒（enchanted 的 L0），
二十条线也可以只在最后 5 秒集体登场。

### 2.6 平均值会骗人：探窗的 89% 集中在最后 30 秒

把探窗的事件按 10 秒分桶：

| 区段 | 帧数/10s | 发生了什么 |
|---|---|---|
| 0–10 s | 737 | 开场动画 |
| 10–80 s | 3 ~ 336 | **正常谱面**，几乎没有演出 |
| **80–115 s** | 2 216 / 5 756 / 5 733 / 2 484 | 终章爆发，占全谱 **89%** |

来源是 **6 条 `blossom*.png` 花瓣线**，实测：

```
每条 1 057 帧位移（moveX ≈ moveY ≈ rotate 极少）
活动区间 85.7 – 114.0 s（约 28 秒）
中位帧间隔 0.027 s  ≈  37 fps
```

也就是说：**这是把"花瓣飘落"参数化后按 37 fps 采样烘焙成关键帧**，
不是逐帧手 K。三条方法论：

1. **平均指标必须配时间分布看。** 帧/音符 46.3 会让人以为"通篇精雕"，
   实际是"75 秒普通 + 30 秒爆发"。
2. **烘焙是正确工程，但 37 fps 是浪费。** 位移采样到 16 fps 肉眼已连续，
   帧数能省掉一半以上（1 057 → ~450）。
3. **一次烘焙能顶掉全谱一半的工作量**，这也是"帧/音符"这类指标容易被单一
   动画段落拉爆的原因——统计时最好剔除 top1 线再看。

```python
# 生成花瓣线的最小骨架（16 fps 采样已够用，别学 37 fps）
bake_curve(lambda b: x0 + amp * math.sin(b * w + phase), 0, 64, bpm=140, fps=16)
```

## 3. 四档目标配置（照着填就能定风格）

拿到一首歌，先选档，再谈细节。

| | A 纯演奏型 | B 演出型 | C 动画型 | D 极简几何型 |
|---|---|---|---|---|
| 参照 | DNA / 西厢寻他 | 鳥の詩 / 声嘶力竭 / 稻香 | enchanted love / 探窗 | **巴拉莱卡** |
| 判定线 | 20~60 | 60~80 | 200+ | 30~50 |
| 非默认贴图线 | 0 | ≤10 | 200+ | **0** |
| 帧/音符 | 3~10 | 10~30 | 20~50 | 20~30 |
| 帧/秒 | 15~40 | 40~100 | 100~160 | 100~160 |
| Drag 占比 | ≤20% | 30%~50% | 30%~55% | 25%~35% |
| Hold 占比 | 5%~10% | 5%~18% | 10%~18% | 10%~16% |
| Flick 占比 | ≤5% | 2%~8% | 2%~8% | ≤5% |
| 变速 | 少而狠 | 中等 | 多但都配画面 | 中等 |
| 工作量重心 | 排布与手感 | 段落转场 | 素材与编排 | **运动设计** |
| 风险 | 同质化 | 演出盖过演奏 | 音符被淹没 | 线阵糊成一片 |

**别混档**：C 档的画面配 A 档的音符密度，会变成"看片不玩谱"；
A 档的线数硬塞 C 档的演出，会变成"线乱飞但没内容"。

D 档值得单独说：**零自制贴图、零 shader，全靠 40 条默认线做出 148 帧/秒**
（《巴拉莱卡》）。它和 C 档的帧/秒一样高，但成本结构完全不同——
C 档烧在画素材，D 档烧在算运动。素材零成本，难度全在"几何美感"。

## 4. 用这张表做自检

自己写完一张谱，跑一遍 `chart_stats.py`，然后问三个问题：

1. 我的 **帧/音符** 落在哪一档？和我想做的风格一致吗？
2. 我的 **Flick 占比** 够不够支撑副歌的爆发？会不会全程 Tap 打字机？
3. 我的 **moveX : moveY** 是画布型还是镜头型？如果是镜头型，
   有没有哪一段 Y 动得太狠，导致读谱失控？

三个问题都答得上来，谱子的定位就清楚了。

## 5. 数据口径与局限

- 时长取音频真实长度（`mutagen`），缺失时回落到"最后一个音符 - 第一个音符"
- `事件帧` 统计 `eventLayers[].*Events` 的关键帧总数（不含 `posControl`）
- `旋转线` 只统计**有效旋转**（|角度| > 0.001），排除编辑器写入的默认 0 帧
- `贴图` 排除默认 `line.png`，所以"0"代表"一张自制图都没有"
- 峰 NPS 用 1 秒滑动窗口，与游戏内实际手感会有 ±15% 偏差

后续如果样本增加到 20+ 张，建议按难度分级重算分位数，
本页的绝对数值只作**量级参考**，不要当成硬阈值。
